# 版本号与自动更新

**简体中文** | [English](#versioning-and-updates-english)

本文约定 TuPigCarPlay 的版本怎么编、构建怎么涨号、以及客户端怎么发现 GitHub Release 上的新包并提示更新。  
检测 / 下载 / 校验在 `common/.../update/`；版本真相源是根目录 `version.properties`；发版见 `.github/workflows/release.yml`。

---

## 1. 版本号规则（语义化）

对外展示用 **`主版本.次版本.修订号`**（SemVer），与 `versionName`、Git tag 一致。

| 字段 | 含义 | 何时加 |
| --- | --- | --- |
| **主版本 MAJOR** | 不兼容的大改：换包名、换签名、会话协议大变、用户必须卸载重装等 | 人工定，谨慎 |
| **次版本 MINOR** | 向后兼容的功能：新设置、新连接能力、明显体验改进 | 发功能向 Release 时 +1，修订号归零 |
| **修订号 PATCH** | 修 bug、文案、小优化、紧急热修 | 发修丁 Release 时 +1 |

**例子**

- `0.0.1` → 修音乐卡顿：`0.0.2`
- `0.0.2` → 加一批零跑设置但不破坏旧数据：`0.1.0`
- 将来要换签名被迫重装：`1.0.0`

预览阶段主版本保持 `0`，表示公开预览、不承诺协议/行为永久稳定。本仓产品号从 **`0.0.1`** 起计（与 DiPlay 的 `0.2.x` 发布号分开）。

### 1.1 和 Android 安装器的关系

| 字段 | 作用 |
| --- | --- |
| `versionName` | 给人看的 SemVer，也是和 Release tag 比对的依据（如 `0.2.22` / tag `v0.2.22`） |
| `versionCode` | 单调递增的整数，系统用来判断「能不能覆盖安装」；**必须每次要上架/发 APK 的构建都比上一份大** |

客户端比较新版本时只看 **SemVer（从 tag / versionName 解析出的三段数）**，不看 `versionCode`。`versionCode` 只服务安装器。

### 1.2 预发布后缀（可选，默认不用）

若将来要发测试包，可用 `0.3.0-rc.1` 这类后缀。正式检测逻辑：**带后缀的包默认不提示给正式用户**（只认「干净」的 `x.y.z` tag）。当前产品路径建议只发正式三段号。

## 2. 版本号管理流程

```
改代码 → 决定涨哪一段 → 打 tag / 出 Release → CI 写出 APK 与校验和
                ↓
        车机后台或关于页拉 Release 列表 → 比 SemVer → 提示 / 下载 / 校验 / 系统安装
```

### 2.1 谁改号、什么时候改

| 场景 | `versionName` | `versionCode` |
| --- | --- | --- |
| 日常本地 `assembleDebug` | **不自动改**（避免开发机刷爆修订号） | 可用本地覆盖，默认跟仓库一致 |
| CI 打 **Release APK** | 与将要发布的 tag 一致（`v0.2.22` → `0.2.22`） | **自动 +1**（相对上一正式包） |
| 热修同功能线 | PATCH +1 | +1 |
| 明确新功能批次 | MINOR +1，PATCH=0 | +1 |
| 破坏性变更 | MAJOR +1，MINOR=PATCH=0 | +1 |

「每次构建自动递增」在本项目里落实为：

1. **每次要发布的 CI 构建**：自动递增 **`versionCode`**（必做）。  
2. **`versionName` / tag**：由发布流程按 SemVer 规则写入，通常与「点发布」绑定，而不是每个 PR 调试构建都涨。  
若需要「每条 main 合入都产可安装包」，可只涨 `versionCode`，`versionName` 仍等正式 Release 再动——这和主流应用商店/大厂内测通道的做法一致。

### 2.2 推荐的仓库落点

- 单一真相源：例如根目录 `version.properties`（或 `gradle/libs` 旁的小文件）存：

  ```
  VERSION_NAME=0.0.1
  VERSION_CODE=1
  ```

- `mobile/build.gradle.kts`（以及若有其它 application 模块）只读这个文件。  
- 发布工作流：校验 tag == `v${VERSION_NAME}` → 组装 APK → 生成 `SHA256SUMS.txt` → 上传到本仓 Release（`Tupig/TuPigPlay`）。  
- 合并进 main 的发布 PR 里顺带改 `VERSION_NAME` / 让脚本改 `VERSION_CODE`，避免人手漏改。

### 2.3 Release 资产约定（和现有客户端对齐）

每个 GitHub Release 至少包含：

1. `TuPigCarPlay-<versionName>.apk`  
2. `SHA256SUMS.txt`（含该 APK 的 sha256）

tag 形如 `v0.2.22`。客户端从 tag 里抠出 `0.2.22` 再和本地 `versionName` 比大小。

## 3. 自动更新：现状与目标

### 3.1 已经有的能力

| 能力 | 位置 / 行为 |
| --- | --- |
| 拉 Release 列表 | `UpdateClient` + `UpdateCatalog` |
| SemVer 比较 | `UpdateVersion.isNewer` |
| 后台检查 | `BackgroundUpdateWorker`：约 24h 周期 + 打开应用约 2 分钟后一次；需联网；会话「正在连接/恢复」时推迟 |
| 开关 | 关于页可关后台检查（默认开） |
| 首页提示 | 有缓存的新版本时显示「有可用更新」，点进关于下载 |
| 下载与安装 | 用户点下载 → 拉 APK + 校验和 → SHA-256 → 交给系统安装器（**不会后台静默装**） |

### 3.2 仓库与发布侧（已对齐）

1. **检测地址**：[`Tupig/TuPigPlay`](https://github.com/Tupig/TuPigPlay) releases API（`UpdateClient.RELEASES_URL`）。  
2. **发布侧**：`version.properties` + Release 工作流涨号 / 打 tag / 上传 `TuPigCarPlay-<version>.apk` 与 `SHA256SUMS.txt`。

### 3.3 参考的大厂策略（落到车上怎么用）

| 常见做法 | 本项目怎么跟 |
| --- | --- |
| 软更新为主，强更慎用 | 默认只提示，不拦开车/投屏；仅 MAJOR 或安全公告才考虑「必须更新」文案（仍建议允许稍后，避免堵在路上） |
| 控制检查频率 | 已有约 24h 间隔 + 打开后延迟；失败退避，不刷爆 GitHub API |
| 用户主动触发 | 关于页「检查更新」立刻查，不受 24h 冷却（可保留「检查中」态） |
| 校验完整性 | 必须校验 `SHA256SUMS`；失败不装 |
| 流量与安全 | 只 HTTPS；不传账号；User-Agent 带当前版本（隐私政策已写） |
| 驾驶干扰 | **不在 CarPlay 全屏会话中弹系统级阻断对话框**；首页/关于提示即可；下载等回应用前台、停车再装 |
| 可关闭 | 保留关闭后台检查；手动检查仍可用 |

不做：静默覆盖安装、强制杀进程升级、未校验的旁路下载源。

## 4. 更新检测逻辑

```
开始检查
  ├─ 后台开关关闭？ → 结束（手动检查除外）
  ├─ 距上次成功检查 < 24h？ → 结束（手动检查除外）
  ├─ 无可用外网？ → 稍后重试
  ├─ 有会话且未稳定（连接中/恢复中）？ → 稍后重试
  ├─ 本地 versionName 解不出 x.y.z？ → 结束（避免开发包常驻横幅）
  ├─ GET GitHub releases?per_page=3
  ├─ 取第一条同时带有 APK + SHA256SUMS 的正式 Release
  ├─ 从 tag 解析远程版本，与本地比 isNewer
  └─ 更新 → 写入本地缓存；否则清空缓存
```

比较规则（已实现）：

- 先比 MAJOR，再 MINOR，再 PATCH；任一段远程更大即「有新版本」。  
- tag 里夹杂其它文字时，用第一段 `数字.数字.数字`（与现网 `UpdateVersion` 一致）。

## 5. 更新提示的触发条件

### 5.1 何时出现「有可用更新」

同时满足：

1. 本地缓存了一次检测结果，且远程 SemVer **大于** 当前 `versionName`；  
2. 用户未关掉相关展示路径（后台检查关掉后，只要缓存还在，进关于仍可看到；清缓存或装上新版后消失）；  
3. 首页芯片 / 关于页状态来自该缓存，**不在**每次绘制时打网。

### 5.2 何时发起检测

| 触发 | 条件 |
| --- | --- |
| 周期性后台 | 后台检查开着；距上次尝试 ≥ 24h；有网；会话不忙 |
| 打开应用后 | 调度约 2 分钟后的一次性检查（同样受 24h / 开关 / 网络 / 会话约束） |
| 用户点「检查更新」 | 立即请求；失败展示错误，不假装有更新 |
| 点「下载」前 | 再拉一次最新 Release，避免用过期缓存 |

### 5.3 何时不提示 / 不打断

- 本地已是最新，或远程没有合格资产（缺 APK 或校验和文件）。  
- 开发包 `versionName` 无法解析为三段号。  
- CarPlay 正在连接或恢复：只推迟检查，不弹窗。  
- 不因「有更新」断开 CarPlay 或自动开始下载。

### 5.4 下载与安装提示

- **有更新**：首页可点提示 → 关于 → 下载。  
- **下载中 / 校验中 / 可安装**：关于页状态机推进；校验失败提示错误并删除不完整文件。  
- **安装**：调起系统安装界面，需用户确认；装完以新 `versionName` 为准，旧缓存会被下次比较清掉。

## 6. 已落地

1. `UpdateClient.RELEASES_URL` → `Tupig/TuPigPlay`。  
2. 根目录 `version.properties`；`:mobile` 从中读 `versionName` / `versionCode`。  
3. `scripts/bump_version.py`（patch/minor/major/code）、`scripts/verify_release_tag.sh`。  
4. `.github/workflows/release.yml`：手动 bump 打 tag；tag 推送后打 APK、`SHA256SUMS.txt` 并发 Release。  
5. 正式通道跳过 draft / prerelease / 带后缀 tag；缺资产的条目跳过继续往下找。  

发版：在 GitHub Actions 里对 **main** 跑 **Release** 工作流并选 bump；或本地 `python3 scripts/bump_version.py patch` 后提交并 `git tag v… && git push --tags`。

# Versioning and updates (English)

[简体中文](#版本号与自动更新) | **English**

**SemVer** `MAJOR.MINOR.PATCH` for `versionName` and git tags (`v0.2.22`). **versionCode** is a monotonic int bumped on every published APK build. Local debug builds should not auto-bump `versionName`.

Release assets: `TuPigCarPlay-<version>.apk` + `SHA256SUMS.txt` on [`Tupig/TuPigPlay`](https://github.com/Tupig/TuPigPlay) releases.

Client checks this repo’s Releases about daily (and shortly after open), compares SemVer, shows a soft “update available” chip, and only downloads/installs after the user taps—with SHA-256 verify. Do not force-update while driving; keep the opt-out for background checks. Version bumps: `version.properties` + `scripts/bump_version.py` + `.github/workflows/release.yml` (see Chinese sections).
